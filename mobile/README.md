# mobile/ — Expo アプリ

タグを撮って洗濯表示を読み、洗い方を出す iOS アプリ（**Expo SDK 54**）。

## SDK は 54 に固定している（上げないこと）

現代の Expo Go は **SDK を1つしかサポートしない**。実機の Expo Go が
「Supported SDK: 54」（Settings → App Info で確認できる）で、App Store に
更新が出てこなかったため、プロジェクト側を 54 に合わせている。

SDK を上げると実機で
「Project is incompatible with this version of Expo Go」になって起動できない。
上げるなら、先に実機の Expo Go の Supported SDK を確認すること。
コード側は SDK 54 と 57 で API 差が無く、動作も同一であることを確認済み。

記号定義・規則エンジン・認識コアは `../lib/` を **Web 版とそのまま共有**している。
Expo（React Native）を選んだ最大の利点がこれで、Swift への移植が要らない。

## 起動

```bash
npm install
npx expo start
```

Expo Go で読み込める（ネイティブモジュールは expo-camera / expo-image-manipulator /
expo-image-picker / react-native-svg のみで、いずれも Expo Go に含まれる）。

PC のブラウザでも開ける:

```bash
npx expo start --web --port 8088
```

ただし **PC のカメラでは1記号100px以上という要件を満たせない**ので、読み取りの確認には
「写真から選ぶ」（スマホで撮ったタグの写真を読み込ませる）を使う。
この経路はブラウザ上で合成タグ画像を流し込んで検証済み。

## 検証コマンド

```bash
npm run typecheck                       # tsc --noEmit
npx expo export --platform ios          # Metro が実際にバンドルできるか
node ../tools/verify_combine.cjs        # 「まずこれだけ」と「まとめて洗う」の判断
node ../tools/verify_frame_crop.cjs     # 白い枠 → 画素座標 の変換
node ../tools/verify_scan_crops.cjs     # 実写15枚で切り抜きの生成（写真が要る）
```

`../lib` を跨いで import しているので、**Metro の解決が壊れやすい**。
`metro.config.js` を触ったら必ず `expo export` を通すこと。型チェックだけでは検出できない。

実例: `resolver.disableHierarchicalLookup = true` を付けていたせいで、SDK 54 で
`node_modules/expo/node_modules/expo-asset` を解決できずバンドルが落ちた。
SDK 57 では依存がトップレベルに巻き上げられていたので気づけなかった。

## 画面の流れ

```
①読み取る（入口）─┬─ ②撮る前に → ③カメラ（白い枠で切り出す）─┐
                   │                                             ├→ ③'オレンジの枠で範囲を決める
                   │  「写真から選ぶ」（白い枠は無い）──────────┘        ↓
                   │                                              ④読み取り中 → ⑤読み取りの確認 ─┐
                   │                                                     ↑              │        │
                   │                                        「もう一度読み取る」（枠は前回のまま）│
                   └─ 手で選ぶ → ②'1分類ずつ7回 ──────────────────────────────────────┤
                                                                                                  ↓
                                                        ⑥洗い方と注意点 → ⑦服の情報 → ⑧マイクローゼット
                                                                                                  ↓
                                                                              ⑨服の詳細 ／ ⑩まとめて洗う
```

切り出しは2段構え。**白い枠**は構図の目安（撮った直後に自動で切り出す）で、
そこから**オレンジの枠**で人が最後の範囲を決める。手持ちで撮る以上、白い枠だけでは
必ず余白や隣の文字が入るため。

どちらの経路も**人が「確定」を押すまでは下書き**で、⑤を飛ばして⑥へ行く道は作らない。

## 設計上の約束（変えると安全性が壊れる）

`../IOS.md` に測定の根拠。数字を確かめずに緩めないこと。

1. **読み取り結果は下書き。** 必ずピッカーに流し込み、人が確定する。
2. **1記号110px未満なら下線の本数を `null` にする。** `0` を返してはいけない。
   実測で下線の誤りは100%が過小方向であり、それが「弱い洗濯指定を通常洗濯だと言う」という
   最も危険な誤り方向と一致する。
3. **1位と2位のテンプレート相関の差が0.03未満なら「要確認」表示。** 相関の絶対値では
   当たり外れが分離しないことを実測済み。
4. **存在しない記号の組み合わせを、近い記号へ丸めない。** unknown にする。
5. **記号の列を写真から自動で探さない。人に囲んでもらう。**
   自動検出（Stage 1）は実機で6個中1個しか当たらなかった。一方、切り出し済みの
   記号を見分ける工程は実測で97〜100%。難しいのは検出であって分類。
   囲んでもらえば、その工程が消えるうえ、原寸で切り出せるので1記号あたりの
   ピクセル数が上がり、処理する画素数も減って速くなる。

   **切り出しは2段構えにした**（b20）。白い枠（撮る前の構図の目安）で粗く切り、
   そのうえでオレンジの枠を人が動かして最後の範囲を決める。白い枠だけで済ませると、
   手持ちで撮る以上どうしても余白や隣の文字が入り、段の高さの見積もりが狂う。
   人が範囲を決めるという約束は変えていない（自動検出には戻していない）。
   写真から選んだときは白い枠が無いので、写真そのものにオレンジの枠を合わせてもらう。
   確認画面の「もう一度読み取る」は、**前回の枠のまま**この画面へ戻る。
   毎回引き直させると、直したいのは1箇所だけなのに全部やり直しになる。
6. **読み取り中と確認の画面には、認識器が見た画像を出す。**
   撮った写真をきれいに出すと、失敗したときに「ちゃんと写っているのに」で
   話が終わる。切り出して縮めたグレースケールをそのまま見せれば、
   小さい・暗い・文字を拾っている が人の目にも同時に分かる。

   読み取りが終わるまでの間も**空白にしない**。認識器の画像はまだ無いので、
   撮った写真をオレンジの枠のところだけ切って出しておき、終わったら同じ場所で
   認識器の画像＋記号の枠に入れ替える。何を読んでいるのか見えていれば、
   止まっているのかどうかで不安にならないし、枠がずれていたこともその場で分かる。
7. **選び直す画面には、その記号の切り抜きを一緒に出す。**
   分類の一覧を開いた時点で「さっきの記号がどんな形だったか」は忘れる。
   戻って見比べさせない。手で選んだあとは、その行の表示も選んだ記号に変える
   （データだけ入って見た目が「読めなかった」のままなのが、いちばん困る状態）。
8. **ネイティブの画像はその場で手放す（`release()`）。**
   1回の読み取りで数十MBを触る。GC 任せにすると、何回か読んだあとに
   iOS が画像を作れなくなり `saveAsync` が
   "Cannot create image data for given image format" で落ちる（実機で発生）。
   base64 も経由しない。書き出した PNG をファイルから読んで、すぐ消す。
9. **「撮ってから結果が出るまで」に、結果に要らない処理を入れない。**
   体感の待ち時間はそこで決まる。記号ごとの切り抜きは確認画面でしか使わないので、
   画面が出てから作る（実写20枚で 20ms/枚 ぶん。PCの値なので実機ではその数倍）。
   全体1枚ぶんだけは、読み取り中の画面が枠を重ねる下地に要るので同時に作る。
10. **保存するのは記号だけ。洗い方の文章は保存しない。**
   規則（`../lib/plan.ts`）を直したときに、過去に保存した服にもその修正が効く。

## 未検証

- **実機で動かしていない**（この開発環境に iOS 実機・シミュレータが無い）。
  型チェック・Metro バンドル・ブラウザでの通し実行（写真から選ぶ経路）までは通っている。
- **カメラでの撮影経路は未検証。** 「写真から選ぶ」経路と画像デコードは検証済みだが、
  `CameraView.takePictureAsync` から先は実機でしか確かめられない。
- **プレビューが本当に cover で表示されるかは実機でしか分からない。**
  計算そのものは `node ../tools/verify_frame_crop.cjs` で確かめてあるが、
  「画面に映っているものと撮れた写真の関係」は端末の実装しだい。
  ずれていれば③'の画像がタグからずれて見えるので、その場で枠を動かせば足りる。
- **写真から選ぶ経路で、大きさを返さない実装がある**（web の ImagePicker が 0 を返した）。
  返ってこないときは `Image.getSize` で測り直している。実機での挙動は未確認。
- **服の写真の保存先（`expo-file-system`）は実機で未確認。** ブラウザでは複製せず
  元の URI をそのまま使う経路しか通っていない。
- **`saveAsync` が落ちる件（b20 で直した）の再発確認は実機でしかできない。**
  `release()` を入れ、base64 を経由しないようにし、失敗したら一段小さくして
  1度だけやり直すようにした。ブラウザでは再現しない類の不具合なので、
  実機で「10回続けて読み取る」を試すこと。
- **実物のタグでの精度は未評価。** 合成データでの測定しかない。
- Stage 3（記号の中の文字の読み取り）は未実装。桶の誤りの大半はこれが原因。
