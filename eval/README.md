# eval/ — 実写での評価セット

合成データでいくら測っても、実物との差は埋まらない。
実際に撮ったタグの写真を基準にするための一式。

**`public/` から移してある。** Next.js の `public/` は静的配信ディレクトリなので、
Vercel にデプロイすると誰でも URL で取得できてしまう。評価データを置く場所ではない。

## 中身

| | |
|---|---|
| `photos/test_N.heic` | 実物の衣類タグの写真（iPhone、3024x4032）。**git には入れていない**（公開リポジトリのため。ローカルにのみ置く） |
| `crops.json` | 各写真の「記号がある範囲」（元画像の画素座標）。アプリで人が囲む操作の代わり |
| `results_2026-08-20.xlsx` | 手作業で数えた検出率・反映率・正答率 |

写真が無い環境では実行できない。手元にタグの写真を用意して `eval/photos/` に
`test_1.heic` … の名前で置けば、同じ手順で測れる。

## 実行

```bash
python tools/prep_real.py eval/photos tools/.build/realraw eval/crops.json 1400
node tools/build_vision.cjs
node tools/eval_real.cjs tools/.build/realraw tools/.build/realout
```

`report.json` に、記号ごとの一致テンプレート・相関・マージン・確定結果が出る。

## この10枚から見つかった問題（2026-08-20）

合成データでは一度も出なかったものばかりだった。

1. **下線を捨てていた** — 罫線を除く条件（極端に細長い成分）が、
   「弱い洗濯」の下線を巻き添えにしていた。集計表の `142->140` `151->110` がこれ。
2. **記号列が1段しかない前提だった** — 10枚中5枚が2段組。2段目が丸ごと無視され、
   検出が `3/7` や `1/6` に落ちていた。
3. **「一番背の高い成分」を基準にしていた** — 服の影のような塊が1つあるだけで
   基準が跳ね上がり、記号が全部候補から外れて検出0になった。
4. **傾き** — 実写は必ず数度傾く。それだけで相関が 0.7台から 0.3台に落ちる。

## 2回目のテストで分かったこと（2026-08-20 ver_2）

検出は 45/63 -> 60/63 に改善し、10枚中8枚が過不足なしになった。
一方で「反映されなかった」記号に強い偏りが出た。

- **`300`（タンブル乾燥NG）が10件中10件で反映されず**
- **`445`（日陰のつり干し）が8件**

`445` は原因が判明した。**日陰の斜線の向きが逆だった**（本人の指摘）。
公式リーフレットを実測したところ、右上から左下（`/`）が正しく、
こちらは左上から右下（`\`）に引いていた。修正済み。

`300` は棄却ではなく**誤認**だった（実写でアイロンNG `500` に化けていた）。
×付きの記号はどれも「基本形＋大きな×」で、×が面積を占めるため相関を支配し、
基本形の違いが埋もれる。

### ×を消してから基本形を判定する案（試して取り下げ）

対角線の被覆から×を検出し、その近傍を消してから基本形だけを照合する案を実装した。
×の検出自体は正確だった（43記号中42個正解、誤検出1）。
しかし合成タグの正解率が 90〜100% -> 75〜88% に悪化。
装飾なしの基本形テンプレートを別に用意しても 70〜81% で、さらに悪化した。
×を消すときに基本形の一部まで削れているのが原因と思われる。**取り下げた。**

別の筋（基本形を幾何特徴で判定する、×の位置を使って基本形だけを切り出す等）が要る。

## まだ解けていないこと

- **実写での相関が 0.34〜0.62** で、合成（0.7〜0.9）に届かない。
  テンプレートと実物の印字にまだ差がある。
- **test_3（湾曲したタグ）と test_4（暗いタグ）は検出できていない。** 台形補正が要る。
- **×記号どうしの混同**（200/300/500/600）。×が強すぎて基本形の差が埋もれる。
  基本形を先に判定する2段構えが要る。

## 増やすときの注意

記号の出現頻度は実物では極端に偏る（40℃通常・タンブル禁止・アイロン中温ばかり）。
41記号のうち大半は実物では1件も出ない。**合成データ（tools/）と併用すること。**
