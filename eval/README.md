# eval/ — 実写での評価セット

合成データでいくら測っても、実物との差は埋まらない。
実際に撮ったタグの写真を基準にするための一式。

**`public/` から移してある。** Next.js の `public/` は静的配信ディレクトリなので、
Vercel にデプロイすると誰でも URL で取得できてしまう。評価データを置く場所ではない。

## 中身

| | |
|---|---|
| `photos/test_N.heic` | 実物の衣類タグの写真（iPhone、3024x4032）。**git には入れていない**（公開リポジトリのため。ローカルにのみ置く） |
| `crops.json` | 各写真の「記号がある範囲」（元画像の画素座標）。アプリで人が囲む操作の代わり |
| `crops.json` にある矩形 | 記号列を囲む範囲。写真を全画面で見て引き直した（test_1/6/8/9 は記号が枠から外れていた） |
| `truth.json` | **写真を拡大して1枚ずつ目視で起こした正解**（63記号）。`uncertain` は判別しきれなかったもの |
| `results_2026-08-20.xlsx` | 手作業で数えた検出率・反映率・正答率 |

写真が無い環境では実行できない。手元にタグの写真を用意して `eval/photos/` に
`test_1.heic` … の名前で置けば、同じ手順で測れる。

## 実行

```bash
python tools/prep_real.py eval/photos tools/.build/realraw eval/crops.json 1400
node tools/build_vision.cjs
node tools/eval_real.cjs tools/.build/realraw tools/.build/realout
```

`report.json` に、記号ごとの一致テンプレート・相関・マージン・確定結果が出る。

採点はこちら。手集計ではなく `truth.json` と突き合わせる。

```bash
node tools/score_real.cjs tools/.build/realraw
```

## 手集計の正解表には取り違えがある

3回目の集計（ver_3）と写真を突き合わせたところ、いくつか食い違いがあった。

- test_2 / test_6 / test_10 の自然乾燥は **`425`（日陰平干し）** で、`445`（日陰つり干し）ではない。
  四角の中の線が横なら平干し、縦ならつり干し。
- test_5 の1個目は手のマークなので **`110`（手洗い）**。集計表は真値を `190`（95℃洗濯機）としている。
- test_5 の2個目は三角に×なので **`200`（漂白不可）**。集計表は真値を `210` としている。
  ただし test_8 の三角は斜線2本なので `210` で、こちらは集計表が正しい。

正答率はこの取り違えのぶん低く出ている。以後は `truth.json` を正解とする。

## この10枚から見つかった問題（2026-08-20）

合成データでは一度も出なかったものばかりだった。

1. **下線を捨てていた** — 罫線を除く条件（極端に細長い成分）が、
   「弱い洗濯」の下線を巻き添えにしていた。集計表の `142->140` `151->110` がこれ。
2. **記号列が1段しかない前提だった** — 10枚中5枚が2段組。2段目が丸ごと無視され、
   検出が `3/7` や `1/6` に落ちていた。
3. **「一番背の高い成分」を基準にしていた** — 服の影のような塊が1つあるだけで
   基準が跳ね上がり、記号が全部候補から外れて検出0になった。
4. **傾き** — 実写は必ず数度傾く。それだけで相関が 0.7台から 0.3台に落ちる。

## 2回目のテストで分かったこと（2026-08-20 ver_2）

検出は 45/63 -> 60/63 に改善し、10枚中8枚が過不足なしになった。
一方で「反映されなかった」記号に強い偏りが出た。

- **`300`（タンブル乾燥NG）が10件中10件で反映されず**
- **`445`（日陰のつり干し）が8件**

`445` は原因が判明した。**日陰の斜線の向きが逆だった**（本人の指摘）。
公式リーフレットを実測したところ、右上から左下（`/`）が正しく、
こちらは左上から右下（`\`）に引いていた。修正済み。

`300` は棄却ではなく**誤認**だった（実写でアイロンNG `500` に化けていた）。
×付きの記号はどれも「基本形＋大きな×」で、×が面積を占めるため相関を支配し、
基本形の違いが埋もれる。

### ×を消してから基本形を判定する案（試して取り下げ）

対角線の被覆から×を検出し、その近傍を消してから基本形だけを照合する案を実装した。
×の検出自体は正確だった（43記号中42個正解、誤検出1）。
しかし合成タグの正解率が 90〜100% -> 75〜88% に悪化。
装飾なしの基本形テンプレートを別に用意しても 70〜81% で、さらに悪化した。
×を消すときに基本形の一部まで削れているのが原因と思われる。**取り下げた。**

別の筋（基本形を幾何特徴で判定する、×の位置を使って基本形だけを切り出す等）が要る。

## 3回目のテストと、写真の質への対処（2026-08-20 ver_3）

本人の見立て（「精度は写真に依存する。4枚目は衣服の配色が違うから、
3枚目は生地が傷んでいるから」）は当たっていた。原因まで特定できた。

### test_4 は「黒い生地に白いプリント」だった

二値化が `インクは背景より暗い` と決め打ちだったので、**記号が全部背景側に
回っていた**。切り出しが 1/6 で、当然1つも読めない。
Otsu で分けた2クラスのうち、**画像の縁にあるほうを背景**と決めるように直した
（`lib/vision/binarize.ts` の `inkIsDark`）。露出にも生地の色にも依存しない。
黒印字ではこれまでと同じ挙動なので、合成データの数値もパリティも変わらない。

### test_3 は「織り目が記号と同じ太さで写っている」

生地が傷んでいるというより、織り目の陰影が線の太さと同じ大きさで出ていて、
二値化すると記号と見分けがつかない。しきい値では取り除けないので、
**画像そのものを先にならす**（箱ぼかし）ことにした。
中央値フィルタより結果が良く、累積和で1画素あたり定数時間で済む。

ぼかすと細部が溶けるので、**ぼかした画像で記号を探し、元画像で読む**。
ぼかし／原画／その組み合わせの3通りを走らせ、**マージンの合計が最大のもの**を採る
（正解を知らずに選べる基準。傾き補正と同じ考え方）。

最初は「照合できた記号の数＋平均相関」で選んでいたが、これはぼかし側に
系統的に有利で、間違った答えを増やしていた。数ではなくマージンで選ぶ。

### 利用者が枠をぴったり合わせると検出0になっていた

候補の絞り込みに「画像の高さの6割以下」という条件があった。
記号列だけを囲むと記号の高さが画像の8〜9割になるので、**候補が全滅**する。
枠の引き方は利用者次第なので高さでは絞らない。記号は必ず横に2個以上並ぶので、
幅が画像の半分を超えるものだけを外す。

### 結果

`truth.json`（63記号）に対して 再現率 23.8% -> **52.4%**。詳細は `tools/SCAN.md`。

## 4回目のテスト（2026-08-20 ver_4）

**検出 63/63**（全部見つかった）。反映 43/63、そのうち正答 35。
正解に対する最終的な一致は 27/63 -> **35/63**。
こちらの評価環境（`truth.json`）での 33/63 とほぼ揃った。

残る誤りは**細い特徴に集中**している。
`425 -> 420`（日陰の斜線）、`152 / 151`（下線の本数）、`611 -> 610`、
`712 -> 710`、`510 -> 515`（点とスチーム）。いずれも線1本の差。

### 濃淡を強める案は測って取り下げた

「黒よりの色は黒く、白よりは白く」を11通り試して**全部悪化**した（`tools/SCAN.md`）。
この工程はもともと二値化していて、それが濃淡を強める操作の極限にあたる。
しきい値は写真ごとに Otsu が選び直すので、単調なカーブは効かない。
作業解像度を上げる案も 1000〜2600px で測って、1400px が最良だった。

### 枠を傾けられるようにした

タグは手で持って撮るので必ず傾く。軸に平行な枠しか引けないと、記号列を
全部入れようとして上下の文字を巻き込む。枠ごと傾けられれば記号列だけを囲める。

切り出しは「外接矩形をネイティブで切って縮め、傾いた中身を一度の走査で抜く」。
切り出し・回転・拡縮を別々にかけると補間が3回入って像が甘くなるため。

`tools/verify_oriented.cjs` で機構を確認した。傾き0で取り直すと元と完全に同じ
（33/63）、10度傾けた写真を10度の枠で取り直すと 22/63 まで戻る
（補間が2回入るぶんの目減り。実際の撮影では1回で済む）。
**ただし手元の10枚には、傾けることで結果が変わるほど傾いた写真がない。**
効果そのものは未実測。

## 5回目のテストと、測定そのものの限界（2026-08-20 ver_5）

正解に対する一致は ver_3 27/63、ver_4 35/63、ver_5 31/63。
**ver_4 と ver_5 の間でコードは記号の読み取りに関して何も変えていない**
（枠を傾ける機能を足しただけ）。それでも4記号動いた。
つまり**撮り方だけで ±4 程度は動く**。これは今追いかけている改善幅と同じ大きさで、
1回のテストの差では良し悪しを判定できない。

対策として、線の太さ違いのテンプレートを入れて 33 -> 36 に上げた（`tools/SCAN.md`）。
ただしこれも +3 なので、**この10枚だけでは有意とは言えない**。
合成データとパリティで壊れていないことは確認済み。

### 次に測るなら

1. **同じタグを5回撮って、ばらつきを数字にする。** これが分からないと、
   改善したのか撮り方が良かったのかを区別できない。いま最も足りていない情報。
2. **持っていない記号のタグを足す。** この10枚には19種しか出てこない（全43種）。
   特に足りないのは 平干し系（`420/410/415`）、タンブル乾燥可（`320/310`）、
   40℃以外の洗濯温度、`700`（ウェット禁止）、`530`（アイロン高温）。
3. **同じ記号で印字が違うタグ。** 太さ違いのテンプレートが効いたのは
   印字のばらつきが本体だから。別メーカーのタグでどれだけ違うかを見たい。

## 同じタグを5回ずつ撮ったら（2026-08-21 5件×5）

新しいタグ5枚（test_11〜15）を、それぞれ**5回別々に撮って**測ってもらった。
前回いちばん欲しかった「ばらつき」の数字が出た。

| 回 | 1回目 | 2回目 | 3回目 | 4回目 | 5回目 |
|---|---|---|---|---|---|
| 正解（29記号中） | 17 | 18 | 16 | 18 | 19 |

平均 17.6、幅 16〜19。**同じタグ・同じアプリでも 3記号（10ポイント）動く**。
標準偏差はおよそ 1.1記号。
つまり **29記号の集合で 2記号（7ポイント）未満の差は、1回のテストでは
撮り方のばらつきと区別がつかない**。改善を測るときはこれを基準にする。

タグごとの内訳:

| タグ | 5回の正解 | 幅 |
|---|---|---|
| test_11 | 2,1,2,3,3 / 5 | 2 |
| test_12 | 5,5,5,5,5 / 7 | **0** |
| test_13 | 4,3,4,3,3 / 6 | 1 |
| test_14 | 2,5,2,4,4 / 6 | **3** |
| test_15 | 4,4,3,3,4 / 5 | 1 |

test_12 は5回とも同じ結果になる一方、test_14 は 2〜5 まで振れる。
**ばらつきはタグごとに大きく違う**ので、「アプリのばらつき」という一つの数では
語れない。撮りにくいタグを見つける手がかりになる。

### 表に無い記号が実物にある

test_11 の5個目は**中身のない円**で、JIS L 0001 の43記号に無い。
アプリはこれを 610（円の中に F）として出してしまう。
一番近い記号に丸めるのではなく「表に無い」と言うべきで、これは未対応。

### 集計表の正解を1件直した

test_15 のアイロンは点が2つなので `520`。集計表は `510` を真値としていた。

## まだ解けていないこと

- **実写での相関が 0.34〜0.62** で、合成（0.7〜0.9）に届かない。
  テンプレートと実物の印字にまだ差がある。
- **ぼかしが細部を溶かす。** `425 -> 420`、`152 -> 150` のように
  日陰の斜線と下線が消える。切り出しと読み取りを分けて一部は戻したが、
  取り切れていない（`445` 4件、`425` 3件、`152` 3件）。
- **×記号どうしの混同**（200/300/500/600）。×が強すぎて基本形の差が埋もれる。
  基本形を先に判定する2段構えが要る。

## 増やすときの注意

記号の出現頻度は実物では極端に偏る（40℃通常・タンブル禁止・アイロン中温ばかり）。
41記号のうち大半は実物では1件も出ない。**合成データ（tools/）と併用すること。**
